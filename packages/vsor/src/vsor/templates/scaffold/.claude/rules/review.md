# Review

**The agent writes; the human checks.** The site is preview and review — it is not an editor, and
it is not an approval.

## What that means in practice

- **Nothing lands unread.** Before you say a document is done, run `vsor dev` and read the
  rendered page the way a reader will — top to bottom, not by diffing the markdown you just wrote.
- **Small, reviewable changes.** One document, or one tight group of documents, per change. A
  forty-file rewrite cannot be reviewed, so it will not be reviewed, so it is not governed.
- **Flag, do not smooth.** Ambiguity, contradiction, a source that looks wrong, a number you could
  not verify — these go to the owner, marked, in the change. Resolving one quietly is the single
  fastest way to put an unchecked claim into a corpus that promises checked ones.
- **Say what you did not do.** "I converted sections 1–4; section 5 references an appendix I did
  not have" is a better report than a clean one that hides the hole.
- **Do not commit for the owner unless asked.** Leave the change reviewable in the working tree.

## Files you never edit by hand

| Path | Why |
| :--- | :--- |
| `build/` | generated by `vsor build`; every edit is erased by the next one |
| `.vsor/` | scratch and the managed site runtime; disposable by design |
| `build.lock.json` | the record of a build — written by `vsor build`, read by humans |

Editing generated output to fix what a page looks like is always the wrong layer. The look lives
in `site/`; the content lives in `knowledge/`.

## Secrets

`.env` holds the project's two secrets and is git-ignored. Never paste its values into a command,
a document, a commit message, or a chat reply — and never move a secret out of it "temporarily".
