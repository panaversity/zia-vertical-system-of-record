# `vsor build` and `vsor dev` — the site half

**Business claim:** the five-minute promise. `vsor init` → add markdown → `vsor dev` shows a live
site; `vsor build` emits a deployable one — the user never touching Node, npm, or a config they
didn't author. Slice 1 scope: the website surface only; the MCP/database half extends this spec at
slice 2.

## Observable contract

**Preconditions, stated not assumed.** Node ≥ 20 and npm on PATH. Absent **or too old**: exit 3
`error: missing-runtime`; the remedy names what was measured ("found node 18.19, need ≥ 20") and
the install (nodejs.org or brew/apt; a framework-managed runtime is a recorded post-v0 upgrade).
First run needs the network for `npm ci`; failure is exit 3 `error: install-failed` with npm's own
stderr passed through untranslated — npm knows whether it was the registry, the disk, or a peer
conflict; we do not guess. Everything installed **in the project** lands under `.vsor/` — `site/`
never gains `node_modules`, the project root never gains `package.json` (init's negative contract
holds for every verb). npm's global cache stays in `$HOME`, as npm always has it.

**What the wheel ships — the transport, decided.** The vsor wheel carries as wheel data under
`vsor/_site_runtime/`: **`sor-site-app.tgz`** — the whole forked site — plus one `lib-*.tgz` per
content-pipeline package (nine at 0.1.0), the shell `package.json` template, and the shell
**`package-lock.json`** *(amended 2026-08-14: this clause named `sor-site-mdx.tgz` and
`sor-site-theme.tgz`, which the fork superseded; the expected set is derived from the shell
manifest's own `file:` dependencies rather than restated here, so the two cannot drift again)*.
A `make wheel` step (`npm ci` + workspace builds + `npm pack` in `packages/sor-site`) **must
precede** `uv build`; hatchling force-includes name each artifact, and a wheel-content test asserts
the app tarball carries `package/src/theme/MDXComponents.tsx` and its vendored font files — the
gate that enforces the ordering. Tarballs, not directories:
npm *copies* a tarball into `node_modules` (normal resolution — no symlink-realpath walk into
site-packages, no `prepare` firing at install time, nothing compiled inside the uv cache). Nothing
generated is committed — the compile is a build-time gate, consistent with the no-vendoring rule.
This is a real vsor→sor-site build-time coupling; AGENTS.md's "couples only via `build.lock.json`"
is amended in this change.

**The runtime shell — materialization and staleness.** Both verbs materialize
`.vsor/site-runtime/`:

- the two `.tgz` files **copied in** from the wheel; a generated `package.json` referencing them by
  **relative** `file:./sor-site-mdx.tgz` paths (no absolute path into the uv cache — the shell
  survives `uv cache prune`, and a vsor upgrade changes nothing behind its back), plus Docusaurus,
  React, and `@easyops-cn/docusaurus-search-local` at **exact versions** whose one home is the
  template in `packages/vsor/src/vsor/templates/`;
- the shipped `package-lock.json` (machine-independent: only relative refs); install is `npm ci`;
- the authored `site/` and `knowledge/` **copied in on every invoke**, with `siteDir` being
  `.vsor/site-runtime` itself *(amended 2026-08-14 — this paragraph specified symlinks and required
  its own amendment if the live walk disproved them; it did, twice: Docusaurus realpaths `siteDir`,
  which walks module resolution out of the shell, and webpack realpaths markdown resources, which
  detaches the docs plugin's metadata and kills every page in SSG. The spec authorized copy-on-invoke
  as the recorded fallback, and that is what ships)*. The copy is wiped and rewritten each run, so
  the authored files remain the single source and an edit is always what the next build sees — the
  acceptance's config-edit row is the live proof. **The accepted cost, stated:** every `vsor build`
  copies the whole corpus, which is linear in corpus size rather than free;
- **`.materialized.json`**, written only after `npm ci` succeeds:
  `{vsor, package_json_sha256, lock_sha256, app_sha256}` *(the fourth key added 2026-08-14: the app is unpacked over the shell rather than installed into `node_modules`, so nothing else would notice a changed fork)*. Each run reuses the shell **iff** the stamp matches
  the freshly generated bytes; mismatch or absence (an interrupted install never writes it) wipes
  and re-materializes. This is what keeps an upgraded vsor from silently building with old JS.

First run on either verb prints one owned line — `installing site runtime — one time, ~1–2
minutes` — then streams npm's own output unmodified. Second run prints neither. The shell is
scratch: deleting `.vsor/` costs a re-install, never work.

**`vsor dev`.** Docusaurus dev server, bound to **127.0.0.1 only** — no `--host` at v0 (settled
decision 12's fail-safe posture applies verbatim to a pre-review corpus). `--port`: integer
1–65535, else exit 1 `error: bad-port`; default 3000. The port is checked by pre-binding before
the child spawns: occupied → exit 1 `error: port-in-use`, naming the port and `--port` — never a
prompt, never silent auto-increment (an agent that printed "localhost:3000" must not be wrong).
The child runs in its own process group; SIGINT/SIGTERM forward to the group; after `vsor dev`
exits, nothing listens on its port and no descendant survives. Ctrl-C is a **decided exit 0**
(never 130). A content error while serving passes through untranslated and the server keeps
serving — the next save recompiles. If the dev server itself dies, exit 1 `error: dev-failed` with
the child's output as the prose.

**`vsor build`.** Reads `instance.md` (strict per `specs/vsor/instance-format`; parse/validation
failure is exit 1 `error: instance-invalid` naming field, file and fix), builds into
`.vsor/staging/` (`--out-dir`), and on success swaps at the project root: rename `build/` →
`.vsor/prev-build` (when present) · rename staging → `build/` · delete prev-build. A crash between
renames is recoverable — the next run restores `prev-build` before building. `build.lock.json` is
written only **after the swap completes**. Emitted at the root, exactly two things:

- **`build/`** — the deployable static site (gitignored by the scaffold).
- **`build.lock.json`** — the committed record, format 1:

```json
{
  "format": 1,
  "build_id": "<derived — recipe below>",
  "created": "<ISO-8601 UTC>",
  "vsor": "<version that ran>",
  "requires_satisfied": true,
  "corpus": {
    "tree": "<sha256 over the walk below>",
    "git": "<HEAD sha, or null>",
    "documents": [{ "path": "knowledge/…", "sha256": "…" }]
  },
  "site": { "docusaurus": "<version>", "node": "<version>", "lock": "<sha256 of shell package-lock.json>" },
  "non_stock": []
}
```

**The record, normatively.** The corpus walk: regular files under `knowledge/**` only; any path
segment starting with `.` excluded (a Finder-dropped `.DS_Store` never moves a build); paths
NFC-normalized, UTF-8 bytes, LC_ALL=C byte sort; `tree` = sha256 over the sorted
`(path, sha256(bytes))` rows. It hashes the filesystem — what will actually be built;
`git rev-parse HEAD:knowledge` is rejected because a dirty tree would make the record lie (this
answers status.md's held-open corpus-identity question; struck there in this change).
`documents[]` uses the same order — one row per file per settled decision 8; large corpora make a
large committed JSON and that cost is accepted; tooling compares `tree`, never the rows.
`corpus.git` is HEAD **only when** HEAD's `knowledge/` tree equals the hashed tree, else `null` —
the record never names a commit that lacks the corpus it built.
**`build_id`** = sha256 over, NUL-separated, in order: `"1"` (format) · `corpus.tree` · the site
tree hash (same walk rules over `site/**`) · sha256 of `instance.md` bytes · the version tuple
`vsor`∥`docusaurus`∥`node`∥`site.lock`. Changing this recipe requires bumping `format`. `build_id`
identifies **inputs**; byte-identical `build/` output is not promised at slice 1 (the OS-leak
found-live proves it would be false). `created` varies on every rebuild **by design** — a
no-change rebuild is a known one-line diff. `requires_satisfied` =
`packaging.specifiers.SpecifierSet.contains(running, prereleases=True)`; the running version is
init's one rule (importlib.metadata / `VSOR_DEV_VERSION`) — mismatch **warns and records**, never
blocks. The shape is a committed, unit-asserted JSON Schema in `packages/vsor`; format-1 readers
must tolerate any `non_stock` element shape (reserved forward for `vsor eject`).

**Failure honesty — the closed slug set.** Exit 0: success (dev's clean shutdown included).
Exit 1, the user's input speaking: `build-failed` (Docusaurus's own error untranslated — it names
file and line), `instance-invalid`, `bad-port`, `port-in-use`, `dev-failed`. Exit 2: reserved,
unimplemented verb. Exit 3, the environment speaking: `missing-runtime`, `install-failed`,
`build-crashed` (the child died by signal/OOM — remedy names memory and `NODE_OPTIONS`, never
blamed on content). The scaffolded AGENTS.md exit-code table gains these slugs in this change —
amending the init spec's AGENTS.md row with a note, the same mechanism as the config row below.

**Vocabulary and search wired from day one — one enforcement.** The scaffold's
`docusaurus.config.ts` gains `themes: ["@vsor/sor-site-mdx", "@easyops-cn/docusaurus-search-local"]`
— a visible, deletable seam. Its canonical home is **init's ratified config row**, amended there in
this change; this spec points, never restates. The **same change reconciles `assemble.mjs`**: the
stock variant stops injecting what the scaffold now declares (its counted-replace guard stays, as
drift detection), so `make surface`'s browser assertions certify the config `vsor build` actually
emits — one enforcement, literally. Stated coupling: the "unedited scaffold builds" row now depends
on mdx and search-local resolving in the shell — **stock look by default means stock theme, not
stock dependency set**. `@vsor/sor-site-theme` ships in the shell from day one, **inert until the
config names it** — the documented opt-in is a real one-line `themes:` edit that resolves.

## Acceptance

Committed as `tests/acceptance/build.sh` (init's operationalization rule: absolute paths and
`VSOR_DEV_VERSION` only), plus a wheel-content unit test. `build/` is served with
`python3 -m http.server` (the run.sh pattern).

```
- the built wheel contains _site_runtime/{sor-site-mdx.tgz, sor-site-theme.tgz,
  package.json, package-lock.json}; the mdx tgz contains lib/theme/MDXComponents.js
- the unedited scaffold passes `vsor build` with zero edits (closes init's
  "when build lands" clause — that test lands there in this change)
- served build/: homepage 200 with the project name; the example doc renders
- the script writes the specified <Quiz /> fixture doc into knowledge/, rebuilds,
  asserts the quiz component markup in built HTML (built on the real path;
  *renders* is owned by B13 in `make surface`, against builds this verb produced)
- second `vsor build` with package networking disabled succeeds (no install ran —
  the reuse claim, init's offline precedent; no wall-clock assertion) and build_id
  is identical; touch one document: build_id changes, its documents row changes,
  others don't; edit site/docusaurus.config.ts: the next build sees it (the
  symlink mechanism's live proof)
- build.lock.json validates against the committed schema; created varies, build_id
  does not; corpus.git is null when knowledge/ is dirty against HEAD
- interrupted install (stamp absent): the next run re-materializes and succeeds
- no node_modules outside .vsor/; no package.json at the project root
- `vsor dev` on an ephemeral --port: poll GET / for 200; touch a knowledge/*.md;
  bounded poll of child stdout for the recompile line (run.sh's poll pattern, no
  sleeps); SIGINT; exit 0; the port accepts a fresh bind (no orphaned child)
- occupied port → exit 1 error: port-in-use; --port 99999 → exit 1 error: bad-port
- first-run output contains the install notice line and ≥1 npm-originated line;
  the second run contains neither
- node absent → exit 3 error: missing-runtime; node 18 on PATH → same slug, remedy
  names the found version
```

Browser-tier assertions (console clean, no external requests, quiz click-through, search) are
owned by `make surface` against builds produced by this verb — one enforcement, not two. Visual
hot-reload verification belongs to the implement-time checklist (the implement-spec skill), not CI.

## Out of scope

The MCP/database half (slice 2 extends `build`) · deploy targets · the managed Node runtime
(post-v0; the precondition + remedy is v0's honest answer) · `vsor eject` (owns `non_stock`
entries) · `serve` (own spec) · multi-corpus · `--host` on dev (127.0.0.1 only, decision 12) ·
byte-identical `build/` output (build_id is an inputs claim) · a hermetic npm cache under `.vsor/`
(npm's `$HOME` cache is npm's business).
